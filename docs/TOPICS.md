## 关于"一个课题要一周吗"——我要修正自己

**我之前给的时间估计是错的，而且错在方法上。**

我按"每个课题独立设计 + 独立执行"来估工期。但实际上：

### 关键事实：八个课题共用同一套数据采集

| 采集项 | 被哪些课题需要 |
|---|---|
| 推理耗时（TTFT / 总耗时 / tokens/s） | #2 有效上下文、**#3 延迟账本**、#4 成本账 |
| 原始输出全文 + 格式审计结果 | #1 能力解离、**#7 grounding** |
| prompt token 数 → 退化临界点 | #2 有效上下文、#5 退化分类、#6 8GB 边界 |
| 引擎参数配置记录 | #1、#2、#6 |
| 意图分流准确率 + 危险漏判 | #1 能力解离、**#8 选型消融** |

**所以真实结构是：建一次探针，八个课题的数据同时产生。**

我之前那份"分阶段、按课题推进"的计划是错的——它让你以为必须一个一个做。

## 修正后的真实工期

| 阶段 | 内容 | 真实成本 | 覆盖课题 |
|---|---|---|---|

| **S4** | 长会话梯度（R1–R6 × KV 位置） | **半天** | #2 #5 #6 |
| **S5** | 意图分流复跑（已有 134 条基准） | 1 小时 | #1 #8 |

**S1–S6 全部跑完：约 1 天。** 而这已经能支撑 #1 #2 #3 #4 #5 #6 #7 #8 里的**七个**。

不做 S7，#1 的结论要写成"PTQ1 上观察到的"而非"量化导致的"（见 `EXPERIMENT_DESIGN.md` §5）。

**结论：不是一周，是一个半天 + 一天的量。** 我之前把"写报告"也算进去了，那是两回事。

# 课题 #1：三元量化下的能力解离

**权重 21/25 · 独特性 5 · 研究意义 5**

## 叙述

量化文献的默认前提是"损失均匀且小（3–5%）"。这个前提让我们用一个平均分
（MMLU、perplexity）概括量化代价。

但在本项目的目标工作负载上，损失**不是均匀的**：

```
中文意图分流    91%  ██████████ 几乎无损
图像内容理解    准确  ██████████ 无损
GUI 空间定位    归零  ░░░░░░░░░░ 完全失效
长会话稳定性    受损  ███░░░░░░░ 6723 token 即退化
```

**如果这个解离成立，学术意义是直接的**：它说明单一平均分不足以描述极低比特模型的
可用性——因为平均值会把"完全正常"和"完全失效"平均成"轻微下降"。

它还解释了一个日常现象：「我的模型变笨了」这句话是错的。
不是整体变笨，是**特定能力被选择性抹掉**，而这些能力恰好是 GUI agent 所依赖的。

## 为什么现在能测

现有量化研究测 Q8 → Q4 → Q2，而 **Q2 在共识里已经是"垃圾"**，所以没人往下测。
本项目用的是**三值权重（-1/0/+1）**，比 Q2 更极端。

**这个量级几乎无人复现。** 这是独特性 5 分的来源。

## 关键风险（必须写进报告）

**没有同源 FP/Q8 基线 → 不能说"量化导致解离"**，只能说"在 PTQ1 等级上观察到解离"。
补法是 S7 跨模型对照。

## 依赖

探针 S1 + S2 + S3 + S5。**另外 P1 格式审计必须先做**——它可能修正本课题的前提。

# 课题 #2：端侧资源受限部署的有效上下文边界

**权重 21/25 · 大众接受度 5 · 成本效率 5**

## 叙述

**这是八个课题里研究空白最明确的一个。**

我核实过所有相关文献：KV cache 的权威综述算的全是 H100 / H200 / GB200，
讨论的是"怎么在数据中心卡上省显存"，用的是 PagedAttention、FP8 量化、MLA。

**没有一篇讨论"KV cache 放在系统 RAM 里 vs 放在显存里，对有效上下文长度有什么差异"。**

而这正是本项目引擎（KVMem）的核心机制。

三变量矩阵：

```
量化等级（PTQ1 / 其他）
    ×  KV 位置（RAM 6GB / 显存）
        ×  思考模式（on / off）
            → 测有效上下文长度
```

## 为什么大众接受度 5

"我的模型变笨了"是所有本地部署者唯一能立刻搜到答案的问题。
而"跑得动 ≠ 跑得好"这个区分，论坛里全是 anecdotal，没有系统性数据。

## 与 #1 的区别

- **#1 问**：模型能力在量化下如何丢失
- **#2 问**：工程配置如何影响可用性

**#2 不需要跨模型对照**（因为它测的是配置差异，不是模型差异），
所以它比 #1 更容易得出干净结论。

# 课题 #3：端到端延迟账本

**权重 21/25 · 成本效率 5 · 传播力最强**

## 叙述

"本地模型好慢"是所有抱怨里最高频的一句。**但几乎没人拆过账。**

40–70 秒到底花在哪：

```
prefill（读 prompt）      ?
decode（逐 token 生成）   ?
视觉塔前向                ?
量化方式的影响            ?
CPU-GPU 搬运              ?
思考 token 占用           ?
```

已知的一个数据点：**关掉思考，86s → 13s，6.6 倍差距。**
这一个数字就足以让人重新审视"思考模式该不该默认开"。

## 为什么它传播最广

可复现性极高（别人照着就能测）、结论立刻可用（改一个开关就见效）、
**成本几乎为零**（`--kvmem-trace` 已经在记了）。

## 独立成立

**#3 不依赖任何其他课题**。即使只做这一个，也是一份完整的、可复现的延迟账本。

# 课题 #4：本地 vs API 成本账

**权重 21/25 · 可复现性 5 · 独特性 2**

## 叙述

```
本地每月成本 = 一次性硬件摊销 / 使用月数 + 电费
             = tokens/s → 每日可用 token 数 → 覆盖的任务量

API 每月成本 = tokens × 单价 × 调用量
```

## 诚实评价

**这是算术，不是研究。**

它的价值在于**消除争议**：所有"本地还是 API"的讨论最终都回到"到底值不值"，
但大部分人算不清这笔账，因为没人统计过自己真实的日均调用量。

**独特性只有 2 分**——因为方法无新意。但它是唯一**零争议、零主观**的课题。

## 建议定位

**当配菜，不当主菜。** 给 #1 #2 #3 提供一个"所以呢"的落点。

# 课题 #5：五态退化分类法

**权重 18/25 · 唯一可能被引用的东西**

## 叙述

这是项目里唯一**可能被学术界引用**的产出，因为它给一类现象建立了共同语言：

```
EMPTY         模型返回空
TRUNCATED     返回被截断
FIXED_POINT   陷入固定模式重复
SAME_PLAN     重复给同一个计划
SHELL_LOOP    纯工具轮连续 ≥3 次
```

**工程界到处都在遇到卡死和空转，但没有人给它们统一定义。**
大家只能用"模型抽风了""又犯病了"这种描述。

## 附带的一个次级贡献

```
SHELL_LOOP 的检测规则：同一纯工具轮连续 ≥3 次 → 熔断
```

这不是防呆阈值，是**识别出了一个真实的失效模式**（agent 陷入工具调用死循环）
并给出了可推广的检测规则。

## 建议定位

**不当主菜，当 #1 #2 实验里的诊断工具章节。**

理由：五态分类本身是"我观察到的现象"，
**只有放进有对照数据的实验里，它才变成"可引用的分类法"。**

# 课题 #6：8GB 显存的真实边界 —— "跑得动≠跑得好"

**权重 17/25 · 大众接受度 5**

## 叙述

现有内容全是 anecdotal。有一篇专门吐槽这件事，说 **"68% 的分享 demo 跑在双 4090 工作站上"**
—— 而读者的显卡是 8GB。

现成的靶子：

```
模型文件 4.7GB（Q4_K_M 8B）装得下
CUDA 开销 ~0.5GB
计算缓冲 ~0.6GB
─────────────────────
留给 KV cache 只有 ~2.2GB
   ↓
0.1GB / 1K token
   ↓
实际可用上下文 ≈ 16K，而模型标称 128K
   ↓
8 倍差距
```

## 本项目的独特角度

**#6 通常在讲"8GB 装不下什么"，本项目是"8GB 装下了 27B，然后它变笨了"。**

后者是一个**没有人讨论过的场景**——不是装不下，是装下了但不好用。
这个区分才是有价值的部分。

# 课题 #7：GUI grounding 天花板测绘

**权重 16/25**

## 叙述

这是**已经被行业部分覆盖**的课题。OmniParser（微软专门为这个问题做的）自己在
ScreenSpot-Pro 上只有 **39.5%**，而直接用 GPT-4o 是 0.8。

**所以"GUI 定位很难"不是新发现。**

## 本项目还有价值吗

有，但只剩两点：

**1. 排除性证据链（这条仍有价值）**

```
纯色点偏 850px          → 排除"任务太难"
10×10 网格报错位置       → 排除"看不懂"
图缩小偏差反而增大       → 排除"位置编码不够"（418→3088px）
换第二个模型同样不行     → 排除"单模型问题"
```

**2. 格式审计（这个可能反转结论）**

我们此前用严格解析（只接受纯坐标），如果模型答对位置但附带解释文字，
严格解析会记成失败——**人为制造"能力缺失"的假象**。

审计指标 = `严格失败但语义正确 / 总数`。**若 >30%，已有结论要更正。**

## 建议定位

**降为 #1 的一个实验章节，或附录。** 不当主菜。

# 课题 #8：决策模型选型消融

**权重 15/25**

## 叙述

```
Laya          决策准确率 57%   危险漏判 3   → 判定不可用，删除
Qwen3.5-0.8B  决策准确率 91%   危险漏判 0   → 采用
```

## 这是本项目里最标准的一段对照实验

同一个任务（134 条口语化中文意图分类）、同一套指标、两个候选模型。
**方法论上站得住**，比单模型分数报告强一个量级。

## 但方法论上的硬伤

**134 条基准是自建的。** 审稿人会立刻问：

- 这批题目有代表性吗？
- 为什么是这 134 条？
- 换个测试集会怎么排？

**自建基准的 n=1 问题。** 除非能补上公开基准做对照，否则结论不可辩护。

## 建议定位

**当 #1 的"能力解离"的一个证据**——
它正好说明"低比特模型在语义分类上无损"，
是那张四维能力表里的第一行。

**不建议独立成篇。**

# 我建议的组合方式

## 方案 A：一个主菜 + 三个配菜（推荐）

```
主菜   #1 三元量化能力解离
        ├── 数据来源：探针 + KV对照 + 分辨率梯度 + 意图分流
        ├── 诊断工具：#5 五态分类
        └── 落地落点：#4 成本账 + #3 延迟账本
```

**额外价值**：#2 有效上下文边界可以作为 #1 的"工程侧对照"并入，
或者独立成第二篇（它不需要跨模型对照，结论更干净）。

## 方案 B：拆成两个仓库

```
仓库 A（研究向）：#1 + #5 + #7   量化下的能力解离
仓库 B（工程向）：#2 + #3 + #6   端侧部署的有效边界与延迟账本
```

**优点**：两个仓库面向不同读者，检索路径更清晰。
**缺点**：你的独特性主要在 A（因为 PTQ1 没人测过），B 反而撞车严重。

## 方案 C：只做一个最小的

```
只做 #3 延迟账本（半天，trace 已经在记）
```

**这是最低成本的"我完成了一个可复现研究"起点。**
做完你就知道这个项目值不值得继续投入。

# 所有课题共享的硬约束

无论做哪个，以下几条来自项目的既有关键决策，必须遵守：

1. **不得用 `-n` 或客户端 `max_tokens` 硬截思考**（《04-卡死与循环的防治.md》§9 禁令①）。
   限思考只能用 `--reasoning-budget`。
2. **安全默认值全部指向拒绝**：鼠标键盘操作层默认关、白名单默认空、
   组合键与 Enter/Tab 永久拒绝。
3. **实验数据（`experiments/`）不进仓库**，只有 `docs/` 里的结论和图表进。
4. **模型权重与飞书凭证永不提交**。凭证当前为明文，**需先在飞书开放平台重置**。
5. **所有结论必须标注样本量**，小样本的差异不得说成规律。
6. **阴性结果如实报告**。此前最有价值的两条信息（Qwen 其实是视觉模型、
   自研 GUI 框架 UIA 暴露最好）都来自"实测推翻了推断"。
